CLAUDE.md や AGENTS.md に「二重に確認すること」「必ず手順 1 から 6 を順に実行すること」と書いたのは、たぶんモデルが今より指示を軽く扱っていた頃です。モデルが変わると、こうした行は文字どおりに守られて、ツール呼び出しと確認が増えるだけになりがちです。コードも変わるので、存在しないパスや消えたコマンドも残ります。

これを点検するコマンドが、Claude Code に同梱されている `/claude-api prompt-audit` です。名前に `claude-api` と付いていますが、Claude API を使ったアプリ専用ではありません。[監査手順](https://github.com/anthropics/skills/blob/main/skills/claude-api/shared/prompt-audit.md)には、対象は「API を呼ぶアプリ」と「コーディングエージェントの設定ファイル（`CLAUDE.md` / `AGENTS.md`、ルール、スキル、カスタムコマンド、サブエージェント定義、出力スタイル）」の両方だと書いてあります。設定ファイルだけのリポジトリでも使えます。

なお、私はこのコマンドを実際のリポジトリでは走らせていません。コマンドの仕様は公式の文書と手順書を読んだ内容で、後半の例は私が作った架空のものです。

## コマンドの仕様

`/claude-api` は Claude Code の[バンドルスキル](https://code.claude.com/docs/en/skills)で、`prompt-audit` はそのサブコマンドです。Claude Code v2.1.221 以降が必要です。

もう一つの入口が `/doctor prompt-audit` で、v2.1.283 以降です。[メモリのページ](https://code.claude.com/docs/en/memory)によると、中身は `/claude-api` スキルを通して動くので、そのスキルを `skillOverrides` や `disableBundledSkills` で切っていると使えません。

| | `/doctor prompt-audit` | `/claude-api prompt-audit` |
|---|---|---|
| 最低バージョン | v2.1.283 | v2.1.221 |
| 見るもの | 指示ファイル（CLAUDE.md、AGENTS.md、`.claude/` 配下のルール・スキル・コマンド・サブエージェント・出力スタイル） | 上に加えて、アプリのシステムプロンプト、ツール定義、リクエスト設定のコード |

右列の拡張部分は手順書の記述です。`/doctor` 側のページには指示ファイル向けの説明しかありません。

手順書の Step 0 によると、このコマンドは確認の質問をせず、前提を自分で決めて進めます。前提はレポートの冒頭に書かれ、違っていたら絞り込んで再実行します。

- 範囲は、依頼でファイルやディレクトリを指定すればそれ、なければ作業ディレクトリ内の指示ファイル一式です。
- 対象モデルは、依頼で名指ししたモデル、リポジトリが文書化している移行先、コードや文書が指す最新モデルの順で決まります。コーディングエージェントの設定ファイルは、指名がなければ監査を実行しているモデル自身が基準です。

`~/.claude/` の扱いは、2 つの資料で書き方が違います。メモリのページは既定の対象に含めると書き、手順書は依頼で名指ししたときだけとしています。どちらが実際の挙動かは確かめていないので、ユーザー全体の設定を巻き込みたくないなら、パスを指定して実行してください。

出力は 2 つで、どちらも必ず出ます。

- 監査レポート。指摘ごとに場所（`file:line`）、該当パターン、古いと言える理由、確度（高・中・低）、提案する操作が載ります。
- 提案差分。確度が高か中で、操作が `remove` や `rewrite` などの指摘だけが入ります。1 つの変更が 1 つの hunk なので、採用するものだけ選べます。

差分を適用するのは、ユーザーが変更を明示的に頼んだときだけです。その場合も、低確度の指摘や、ファイル間の矛盾・古い事実の修正は、確認なしには適用されません。

## 見つかる指示の種類

手順書は指摘のパターンを 4 グループに分けています。コーディングエージェントの設定ファイルで主に当たるのは最初の 2 つです。

| 見つかるもの | つながる挙動 | 提案される差分 |
|---|---|---|
| 「二重に確認」「徹底的に」のような過剰な指示 | 新しいモデルは文字どおり従うので、ツール呼び出しや出力が増える | 実際に必要な確認だけに書き直す |
| 判断が要る作業の手順 1〜N | 自前の計画のほうが良いのに、台本に従って手数が増える | 達成したいこと・制約・確認方法を書き、順序が本当に大事な所だけ番号を残す |
| 「ツールは必要なときだけ」「呼び出しを最小に」 | 文字どおり守られ、使うべき場面でも使わなくなる | 削除、または使うべき場面を明示 |
| 複数ファイル間の矛盾 | どちらが現行か分からず、読み込み順で挙動が変わる | `git blame` で新しいほうに合わせる。決められなければ指摘だけ残す |
| 実在しないパス、定義のないコマンド | 存在しない場所を探す、失敗するコマンドを打つ | 現在の事実に直す、または削除 |
| 移行先モデルで廃止された API 設定（`budget_tokens` など） | アプリが 400 で落ちる | `effort` など現行の設定への置き換え |

最後の行はアプリ向けです。[コスト最適化のガイド](https://platform.claude.com/docs/en/about-claude/models/optimizing-for-cost-and-intelligence)の出力例では、`budget_tokens` が Opus 5 で 400 を返す件が、他の指摘と違って「これは停止級」と扱われています。コーディングエージェントの設定ファイルでは、リクエストのパラメータを本人が書かないので、手順書もその編集は提案しないとしています。

ツール説明の基準は簡潔さではなく正確さで、引数の意味、制限、失敗条件、何を返さないかが足りなければ、手順書は増やす（`add`）提案をします。減らすのは、`CRITICAL: You MUST use this tool when...` のような煽りや、説明に埋め込まれた使用例・手順です。

「短くする」ことが目的ではないとも、手順書の冒頭にあります。見つけるのは「合わなくなった具体的な指示」で、何もなければ差分は空で終わります。

## 例: 承認ルールと「すべて詳細レビュー」が同居するリポジトリ

以下は私が作った架空の例です。CLAUDE.md にこう書いてあるとします。

```markdown
## 開発ルール
- 設計変更（公開 API、DB スキーマ、モジュール境界）は、着手前に人間の承認を得ること。
  理由: 他チームのサービスが依存しているため。
- すべての修正で、詳細な設計レビューを行い、結果を PR に書くこと。
- 検証は `make verify` で行う。
```

`.claude/skills/review/SKILL.md` には「3. 結果を再度読み直して二重に確認する」という手順があり、Makefile からは `verify` ターゲットが消えて `make check` に変わっています。

手順書の基準で読むと、指摘は 3 つになると私は考えます。

- 「すべての修正で…」は、誤字修正にも設計レビューを書かせるので、ツール呼び出しと出力が増えます（確度は中）。
- `make verify` は Makefile にターゲットがなく、リポジトリ自身が否定している事実なので、確度は高です。
- SKILL.md の「二重に確認」は、古いモデル向けの補強の典型です。

提案される差分のうち CLAUDE.md の分は、次のような形でしょう。

```diff
 ## 開発ルール
 - 設計変更（公開 API、DB スキーマ、モジュール境界）は、着手前に人間の承認を得ること。
   理由: 他チームのサービスが依存しているため。
-- すべての修正で、詳細な設計レビューを行い、結果を PR に書くこと。
-- 検証は `make verify` で行う。
+- 設計に影響する修正は、変更の影響範囲を PR に書く。誤字や文言など設計に影響しない修正は、
+  設計レビューを省いてよい。
+- 検証は `make check` で行う。
```

承認ルールの行は差分に入りません。手順書は、観察できる制約や、理由の書いてある禁止事項を残すとしていて、この行は他チームへの影響という理由を持っているからです。

ただし、レビューの書き直しが承認を弱めないかは、人が見る必要があります。手順書は、禁止を弱める方向の修正は差分にせず指摘だけにするとしています。それでも「設計に影響しない」の判定をモデルに任せると、本来は承認が要る変更が通る可能性が私には気になります。次の比較で見るべき点です。

## 提案を採用するかどうか

私は、その行が何を守っているかで決めます。

- 残すのは、設計上の制約、承認条件、ツールの契約（引数の意味や失敗条件）、今も再現する失敗への対策です。承認条件は、くどくても理由が書いてあれば残します。
- 直すか消すのは、古いモデルの癖への補強、同じことの言い換え、現状と合わないパスやコマンド、他のファイルと矛盾する行です。

「今も再現する失敗か」は `git blame` と `git log` で追えます。手順書も、強調や禁止の行ごとに、どのモデルでどの失敗を防ぐために入れたか、今の対象モデルでまだ起きるかを問うよう書いています。

レポートが保証できるのは、リポジトリで確認できる範囲です。パスが存在しない、コマンドが定義されていない、2 つのファイルが逆のことを言っている、といった指摘がそうです。「この行を消したら挙動が良くなる」はレポートからは分からず、手順書も、前後で小さな動作確認を回すこと、モデルに「この指示は要るか」と聞くのは測定ではないこと、変更は 1 つずつ入れることを挙げています。

先の例なら、同じモデル・同じ依頼で、修正前後の CLAUDE.md を使って 2 種類を比べます。

1. 公開 API のシグネチャを変える依頼で、着手前に承認を求めて止まるか。修正後も止まることが条件です。
2. コメントの誤字を直す依頼で、設計レビューの文章や余計な調査のツール呼び出しが減っているか。

出力は毎回ばらつくので、依頼を数種類用意して複数回走らせ、承認で止まる割合と、ツール呼び出しの回数や所要時間を並べます。承認のほうは 1 回でも抜けたら、その修正の採用は見送ります。

[コスト最適化のガイド](https://platform.claude.com/docs/en/about-claude/models/optimizing-for-cost-and-intelligence)には Anthropic の測定があります。ただし、Anthropic が作った 44 件のサポート問い合わせを、API を呼ぶアプリのシステムプロンプトで解いた結果で、CLAUDE.md を直したときのコーディングエージェントの挙動を測ったものではありません。Opus 4.8 向けのプロンプトを Opus 5 に載せるとコストが 36% 増え、監査後は監査前より 14% 安く、正答率は 92% から 97% でした。Sonnet 4.6 向けのプロンプトを Sonnet 5 で監査すると、精度は同じままコストが 14% 減っています。手元のリポジトリでの効果は、上の前後比較でしか分かりません。

## 試すなら

リポジトリで Claude Code を起動して、セッション内で実行します。

```sh
claude
```

```text
/claude-api prompt-audit
```

範囲を絞るなら、パスを渡します。上の架空のリポジトリなら、こうです。

```text
/claude-api prompt-audit CLAUDE.md .claude/skills/review
```

対象モデルを決めたいなら、依頼文にモデル名を書くのが手順書の優先順位に沿った方法です。レポートは確度の高い順に出るので、パスやコマンドの食い違いのような、リポジトリが否定している指摘から hunk を 1 つずつ取り込み、そのたびに上の 2 種類の依頼で挙動を比べるのが、私のやり方です。
