開発サーバーの Claude Code で始めた調査を、帰宅してノート PC で続けたいと思っても、セッションは実行したマシンの中にしかないので続けられません。シェル履歴の同期ツール Atuin の 18.24 で入った [Atuin Threads](https://blog.atuin.sh/threads-agent-sessions/) は、この場面のための機能です。

```mermaid
flowchart LR
  A["開発サーバーの Claude Code"] --> B["暗号化して同期"]
  B --> C["ノート PC で atuin resume"]
  C --> D["Codex で続きを実行"]
```

著者の Ellie Huxtable さんは、エージェントのセッションを「コマンド、出力、意図、途中で試したことまで入った平文のログ」と書いています。それがホームディレクトリに転がっているだけなのがもったいない、という動機です。Atuin にはもともと、追記型のログを暗号化して同期する仕組みがあり、セッションもその形に収まったそうです。

`atuin resume` で、マシンをまたいでセッションを検索し、再開できます。再開するときに別のエージェントへ fork することもできて、記事の例は Claude Code から Codex への引き継ぎです。対応は Claude Code、Codex、OpenCode のほか Pi と Omp ですが、後の二つは私が詳しくないので説明できません。同期は端末間で暗号化され、運営側は中身を読めないと書かれています。ホスト型のサーバー、自前のサーバー、同期なしのローカル運用から選べて、セッションの取り込みは明示的に有効にする方式です。

## エージェントに過去のセッションを検索させる

私が気になったのは再開より、`atuin mcp install claude` のように入れる MCP サーバーのほうです。入れると、エージェント自身が過去のセッションを検索できます。記事には 2 つ例があります。

1 つ目は障害の調査です。Ellie さんたちがセキュリティ対策としてキーを入れ替えたところ、新しいオブジェクトストレージのキーにアバターのアップロード権限がなく、すぐには気づけませんでした。毎日 Sentry を見ているエージェントが、原因をその日に実行された特定のコマンドまでたどっていました。Ellie さんはその調査結果をまだ読んでいなかったのですが、別のエージェントに「アバターの問題が出ている？」と聞くと、そのエージェントが先の調査セッションを見つけ、原因の特定から修正まで、ゼロからやるより早く進んだそうです。

2 つ目は、採用されなかった試作です。オンボーディングを何度も作り直した経験があり、いま同じ作業をエージェントに頼むと、過去の試作と、なぜやめたのかを持ってきてくれる。main に入らなかったコードや最初のプロンプトがセッションに残っているからで、長い仕様書を書かなくて済む、というのが著者の主張です。

PR や issue に残らない「却下された案」をあとから検索できるのは、確かに便利そうです。ただ、例はどちらも著者自身の体験談で、無関係なセッションが検索に混ざることには触れていません。

## 試すとき

記事の手順はこの 3 行です。私は動かしていません。1 行目はスクリプトを流し込む形なので、中身を読んでから実行するほうがよいと思います。

```
curl --proto '=https' --tlsv1.2 -LsSf https://setup.atuin.sh | sh
atuin resume
atuin mcp install claude
```

同期の前に決めておきたいのは、どこに同期するかです。セッションにはコマンドの出力が丸ごと入るので、出力にトークンなどが混ざっていたら、それも同期の対象になります。暗号化されていても、自前サーバーかローカルのみにするかは最初に選んでおくのがよさそうです。なお公開直後のため、Hacker News のスレッドには私が見た時点で議論がほぼなく、使った人の報告は見つけられませんでした。
